# Fase 13 — Admin Module

## Mutation call signatures (orval v8.23 pattern)

All mutations generated by orval use `{ data: ... }` as the body key, NOT the custom named key:

- **Create (no ID):** `mutate({ data: { ...fields } })`
- **Update (with ID):** `mutate({ id: string, data: { ...fields } })`
- **Delete:** `mutate({ id: string })`

**Why:** orval wraps the request body in a `BodyType<T>` and always uses `data` as the key name regardless of the OpenAPI operationId or schema name. Using the schema name (e.g. `createClientRequest`) causes a TS error.

**How to apply:** Any time a new mutation hook is generated, the call site must use `{ data: ... }` (or `{ id, data }` for updates).

## DataTable empty state

The shared `DataTable` component uses `Empty`, `EmptyHeader`, `EmptyTitle`, `EmptyDescription` sub-components (not props directly on `<Empty>`). The `Empty` component is a `React.ComponentProps<"div">` — it does not accept `title` or `description` props.

**How to apply:** Always render empty states as:
```tsx
<Empty>
  <EmptyHeader>
    <EmptyTitle>{title}</EmptyTitle>
    <EmptyDescription>{description}</EmptyDescription>
  </EmptyHeader>
</Empty>
```

## useListSlots with `enabled`

`useListSlots` options type is `UseQueryOptions<...>` which requires `queryKey`. To pass `enabled: false`, cast as `any`:
```tsx
useListSlots(params, { query: { enabled: condition } as any })
```

## Known limitation — no names on client/professional lists

`GET /api/clients` and `GET /api/professionals` return only `clients`/`professionals` table rows — no `name`, `email` (those are in `users`). Admin screens display id/status/specialty. This is a real UX limitation that requires a new endpoint (JOIN with users) to fix — deferred to a future phase.
