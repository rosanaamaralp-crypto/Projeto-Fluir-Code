Fase 2 — Proposta Técnica do Modelo de Dados
1. Visão Geral do Modelo
O modelo é composto por 14 tabelas organizadas em quatro grupos funcionais:

Grupo	Tabelas
Identidade	roles, users
Domínio de pessoas	clients, professionals, addresses
Serviços e disponibilidade	services, professional_services, availability, blocked_periods, resources
Agendamentos	appointments, appointment_status_history
Transversais	notifications, audit_logs
Princípio central: dados históricos nunca são apagados. Cancelamentos alteram status; desativações alteram status; registros com histórico não são deletados. Toda timestamp é timestamptz (UTC interno, exibição em America/Sao_Paulo).

8. Estratégia de Conflitos
Definição de sobreposição
Dois períodos [A_start, A_end) e [B_start, B_end) se sobrepõem quando:

novo_start < existente_end  AND  novo_end > existente_start

Três camadas de proteção
Camada 1 — Verificação explícita dentro da transação (aplicação)

Dentro de uma transação com SELECT ... FOR UPDATE, antes de criar o agendamento:

-- Conflito de profissional
SELECT id FROM appointments
WHERE professional_id = $prof_id
  AND status NOT IN ('CANCELLED', 'COMPLETED', 'NO_SHOW')
  AND start_datetime < $novo_end
  AND end_datetime   > $novo_start
FOR UPDATE;
-- Conflito de recurso (apenas IN_PERSON)
SELECT id FROM appointments
WHERE resource_id = $resource_id
  AND status NOT IN ('CANCELLED', 'COMPLETED', 'NO_SHOW')
  AND start_datetime < $novo_end
  AND end_datetime   > $novo_start
FOR UPDATE;

Qualquer linha retornada → HTTP 409 APPOINTMENT_CONFLICT.

Camada 2 — EXCLUDE constraint no banco (btree_gist)

Garantia no nível do banco mesmo em caso de bug na aplicação:

-- Requer: CREATE EXTENSION IF NOT EXISTS btree_gist;
ALTER TABLE appointments ADD CONSTRAINT excl_professional_no_overlap
  EXCLUDE USING gist (
    professional_id WITH =,
    tstzrange(start_datetime, end_datetime) WITH &&
  )
  WHERE (status NOT IN ('CANCELLED', 'COMPLETED', 'NO_SHOW'));
ALTER TABLE appointments ADD CONSTRAINT excl_resource_no_overlap
  EXCLUDE USING gist (
    resource_id WITH =,
    tstzrange(start_datetime, end_datetime) WITH &&
  )
  WHERE (status NOT IN ('CANCELLED', 'COMPLETED', 'NO_SHOW')
         AND resource_id IS NOT NULL);

Camada 3 — Transação atômica completa

Todo o fluxo de criação ocorre dentro de uma única transação:

BEGIN
  1. Verificar profissional: ativo + habilitado para o serviço
  2. Verificar serviço: ativo + modalidade compatível
  3. Verificar disponibilidade semanal (availability)
  4. Verificar bloqueios (blocked_periods)
  5. SELECT ... FOR UPDATE no profissional e recurso
  6. Verificar sobreposição explícita (profissional + recurso)
  7. INSERT appointments
  8. INSERT appointment_status_history (criação)
COMMIT

Se qualquer etapa falhar → ROLLBACK libera todos os locks.

Conflito com bloqueios
SELECT id FROM blocked_periods
WHERE professional_id = $prof_id
  AND status = 'ACTIVE'
  AND start_datetime < $novo_end
  AND end_datetime   > $novo_start;

Resultado → HTTP 409 PROFESSIONAL_UNAVAILABLE.

9. Estratégia das Cinco Macas
Representação no banco
Cinco linhas fixas na tabela resources:

name	type	status
Maca 01	MASSAGE_TABLE	ACTIVE
Maca 02	MASSAGE_TABLE	ACTIVE
Maca 03	MASSAGE_TABLE	ACTIVE
Maca 04	MASSAGE_TABLE	ACTIVE
Maca 05	MASSAGE_TABLE	ACTIVE
Cada maca é entidade independente com UUID próprio. O campo appointments.resource_id aponta para exatamente uma maca. Nunca haverá colunas maca_1, maca_2, etc. em appointments.

Seleção de maca disponível
O AppointmentService seleciona a primeira maca livre dentro da transação:

SELECT r.id FROM resources r
WHERE r.type   = 'MASSAGE_TABLE'
  AND r.status = 'ACTIVE'
  AND NOT EXISTS (
    SELECT 1 FROM appointments a
    WHERE a.resource_id = r.id
      AND a.status NOT IN ('CANCELLED', 'COMPLETED', 'NO_SHOW')
      AND a.start_datetime < $novo_end
      AND a.end_datetime   > $novo_start
  )
ORDER BY r.name
LIMIT 1
FOR UPDATE OF r;

Zero linhas retornadas → nenhuma maca disponível → HTTP 409 RESOURCE_UNAVAILABLE (implementa RN-037).

Garantia de não duplicação
A EXCLUDE constraint excl_resource_no_overlap impede dupla reserva mesmo sob concorrência máxima.

Escalabilidade futura
Adicionar "Maca 06" = INSERT de uma linha em resources. Nenhuma coluna de appointments precisa mudar.

10. Estratégia Home Care
Regras do modelo
Regra	Como é garantida
modality = 'HOME_CARE' armazenado no agendamento	Campo appointments.modality
resource_id não pode existir em HOME_CARE	CHECK constraint de modalidade
address_id é obrigatório em HOME_CARE	CHECK constraint de modalidade
O endereço pertence ao cliente do agendamento	Validado na camada de serviço
Nenhuma maca é reservada	Sem INSERT em resource_id; EXCLUDE constraint não afeta
Profissional disponível no horário	Mesma verificação de conflito do presencial
Validação do endereço na camada de serviço
SELECT id FROM addresses
WHERE id        = $address_id
  AND client_id = $client_id;

Zero linhas → endereço inválido ou não pertence ao cliente → HTTP 422 VALIDATION_ERROR.

Prevenção de inconsistências no banco
A CHECK constraint bloqueia silenciosamente qualquer INSERT inconsistente:

HOME_CARE + resource_id preenchido → erro de banco
HOME_CARE + address_id NULL → erro de banco
IN_PERSON + address_id preenchido → erro de banco
IN_PERSON + resource_id NULL → erro de banco
11. Estratégia de Preço e Histórico
Problema
O preço de um serviço pode mudar ao longo do tempo. Agendamentos históricos devem registrar o preço no momento da reserva — não o preço atual.

Dois campos distintos
Tabela	Campo	Significado
services	price	Preço vigente — base para novos agendamentos
appointments	price_at_booking	Cópia do preço no momento da criação — imutável
No momento da criação do agendamento, o backend copia services.price → appointments.price_at_booking. Este campo nunca é atualizado depois, mesmo que o preço do serviço mude.

Preparação para pagamentos futuros
A futura tabela payments pode referenciar appointment_id e usar price_at_booking como base. Nenhuma alteração estrutural em appointments será necessária.

12. Histórico de Agendamento
Fluxo de status e registros em appointment_status_history
Ação	old_status	new_status	Quem pode	reason
Criação	NULL	CONFIRMED	qualquer perfil autorizado	—
Início	CONFIRMED	IN_PROGRESS	PROFESSIONAL	—
Conclusão	IN_PROGRESS	COMPLETED	PROFESSIONAL	—
Cancelamento	CONFIRMED	CANCELLED	CLIENT / PROFESSIONAL / ADMIN	Opcional (cliente), Obrigatório (prof/admin)
Ausência	CONFIRMED	NO_SHOW	PROFESSIONAL / ADMIN	—
Remarcação	CONFIRMED	CONFIRMED	qualquer perfil autorizado	Texto indicando "remarcação"
Nota sobre IN_PROGRESS e cancelamento: agendamento IN_PROGRESS não pode ser cancelado pelo fluxo normal (RN do cancelamento aprovado). Qualquer tentativa de cancelar um agendamento nesse status é rejeitada pela camada de serviço com erro adequado.

Nota sobre remarcação: o status permanece CONFIRMED após remarcação. Um novo registro em appointment_status_history é inserido com reason descritivo e os dados novos de data/horário, permitindo rastrear todas as remarcações.

A tabela é append-only — nenhum registro é atualizado ou excluído.

Alteração de perfil ou status de usuário
O que não gera audit_logs (coberto pelo histórico funcional ou volume muito alto)
Transições normais de status (IN_PROGRESS → COMPLETED pelo profissional)
Leituras de dados
Criação de agendamento pelo próprio cliente (coberta por appointment_status_history)
Campos sensíveis nunca aparecem nos snapshots
password_hash, tokens de sessão e dados de autenticação são excluídos de old_data / new_data antes de qualquer gravação em audit_logs.

15. Segurança
Credenciais
password_hash nunca retornado pela API em nenhuma resposta — excluído nos DTOs de saída
Hashing com bcrypt (custo mínimo 12) ou argon2id
Tokens de sessão não armazenados em texto puro
Dados pessoais
A camada de serviço verifica propriedade antes de qualquer retorno: client_id do token de sessão deve coincidir com o client_id do recurso solicitado
Nenhum endpoint retorna dados de outro usuário sem verificação de role
password_hash e snapshots internos são excluídos de qualquer log
Integridade dos agendamentos
CHECK constraints garantem consistência mesmo com bug na aplicação
EXCLUDE constraints (btree_gist) impedem dupla reserva sob concorrência
Transações ACID garantem atomicidade da criação
price_at_booking e appointment_status_history são imutáveis após criação
Isolamento por perfil
Perfil	Acesso permitido
CLIENT	Somente seus dados, agendamentos e endereços
PROFESSIONAL	Seus atendimentos; dados de clientes apenas no contexto do atendimento
ADMIN	Dados administrativos conforme permissões — nunca acesso irrestrito por padrão
A autorização é sempre verificada no backend. Ocultar menus no frontend é apenas UX — não é segurança.

Auditoria como segurança
audit_logs garante rastreabilidade de todas as ações administrativas. Isso protege contra uso indevido interno e fornece base para investigação de incidentes.

16. Pontos de Atenção
UNIQUE (email) em users: A constraint é simples e permanente. Se um usuário for inativado e outra pessoa quiser usar o mesmo email, o banco bloqueará. Decisão necessária: liberar o email de usuários inativos ou impedir o reuso? Aguarda definição antes da migration.

btree_gist: As EXCLUDE constraints exigem CREATE EXTENSION IF NOT EXISTS btree_gist. Deve estar no script de setup do ambiente de desenvolvimento e na migration inicial.

availability.start_time / end_time sem timezone: Intencional — representa horários locais recorrentes. A aplicação deve sempre interpretar esses valores no timezone America/Sao_Paulo. Qualquer cálculo de slot disponível deve converter start_datetime do agendamento para horário local antes de comparar com os campos de availability.

Remarcação como UPDATE vs. novo agendamento: A proposta trata remarcação como UPDATE no agendamento existente (preserva o mesmo UUID, mantido o histórico na tabela de histórico). Outra abordagem seria cancelar e criar novo — mas isso quebraria a continuidade do histórico para o cliente. Proposta adota UPDATE; aguarda confirmação.

Idempotência de criação: Para o MVP, a EXCLUDE constraint + debounce no frontend é suficiente. Se necessário no futuro, pode-se adicionar idempotency_key uuid em appointments com UNIQUE constraint e TTL gerenciado pela aplicação.

Serviço sem preço: O campo price em services é obrigatório e CHECK (price >= 0). Serviços gratuitos têm price = 0 — válido.

17. Dúvidas ou Conflitos Existentes
17.1 blocked_periods vs. AVAILABILITY_BLOCKS
O prompt da Fase 2 lista AVAILABILITY_BLOCKS, mas os Documentos 13 e 18 usam blocked_periods. São a mesma entidade. A proposta adota blocked_periods, alinhado com os documentos oficiais. Nenhuma divergência real.

17.2 Status PENDING no Documento 14 (RN-051)
O Documento 14 menciona PENDING como status inicial possível. A decisão aprovada da Fase 2 define CONFIRMED. A decisão aprovada prevalece. A proposta omite PENDING do enum de appointment_status para evitar estados órfãos. Se o fluxo mudar futuramente, adicionar PENDING requer apenas uma migration de enum — baixo custo.

17.3 Campo allowed_modalities em services
O Documento 13 não lista explicitamente um campo de modalidade em services, mas as RNs exigem verificação de compatibilidade de modalidade entre serviço e agendamento ("serviço compatível com a modalidade escolhida"). A proposta adiciona allowed_modalities (IN_PERSON, HOME_CARE, BOTH). Aguarda confirmação antes de incluir na migration.

17.4 IN_PERSON sempre exige maca?
O Documento 13 (seção 21) diz "quando necessário" e "quando a operação exigir o recurso". Isso abre espaço para um atendimento presencial sem maca. A proposta assume que no MVP, todo IN_PERSON exige maca — simplifica o modelo e está alinhado com as 5 macas como capacidade total do espaço. Se houver exceção prevista, a CHECK constraint e o fluxo de seleção de maca precisam ser ajustados antes da implementação.

17.5 Motivo de cancelamento pelo cliente
A decisão aprovada define motivo como opcional para o cliente. Isso é implementado com reason TEXT NULL em appointment_status_history + validação na camada de serviço (que exige reason para profissional e admin, não para cliente). Não há conflito, apenas confirmação de implementação.
