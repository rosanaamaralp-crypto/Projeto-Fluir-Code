APROVAÇÃO E EXECUÇÃO — FASE 3

Aprovo a execução da Fase 3 do projeto conforme o plano técnico apresentado anteriormente.

Antes de criar ou modificar qualquer arquivo, siga obrigatoriamente as decisões abaixo.

## 1. DECISÕES APROVADAS

### A. Timezone dos slots

Adotar **UTC puro nesta Fase 3**.

Regras:

* `availability.weekday` será interpretado em UTC.
* `availability.start_time` e `availability.end_time` serão interpretados em UTC.
* O endpoint `/api/slots` receberá `date` em formato `YYYY-MM-DD`, interpretado em UTC.
* Os slots retornados deverão estar em ISO 8601 UTC.
* NÃO adicionar coluna de timezone por profissional.
* NÃO criar nova migration para timezone nesta fase.

Essa decisão deve ser documentada em `docs/FASE-3-...`.

### B. Antecedência dos agendamentos

Adotar:

* `SLOT_MIN_NOTICE_HOURS=2`
* `SLOT_MAX_ADVANCE_DAYS=60`

Os valores deverão ser configuráveis por environment variables, com esses valores como defaults.

Não hard-code os valores diretamente na lógica de negócio.

### C. Primeiro ADMIN

NÃO criar endpoint público `/api/auth/bootstrap`.

NÃO criar ADMIN automaticamente no seed normal.

Criar um **script CLI separado e seguro para bootstrap do primeiro ADMIN**, executável somente manualmente.

Requisitos:

* Deve verificar se já existe um usuário com role ADMIN.
* Se já existir ADMIN, deve recusar a operação.
* Nunca sobrescrever ou alterar um ADMIN existente.
* A senha deve ser informada de forma segura, sem aparecer em logs.
* Usar bcrypt com salt rounds 12.
* O script deve criar `users` com role ADMIN.
* O script não deve criar client nem professional.
* Documentar claramente o comando de execução.

### D. Auditoria

Não registrar absolutamente todos os SELECTs ou operações triviais.

Auditar as operações sensíveis:

* USER_LOGIN
* USER_LOGOUT
* criação de client
* criação de professional
* criação/alteração/desativação de service
* criação/alteração/desativação de resource
* criação/alteração/desativação de professional_service
* criação/alteração/desativação de availability
* criação/cancelamento de blocked_period
* alterações relevantes de dados de client
* alterações relevantes de dados de professional
* alterações de endereço
* alterações de status
* operações administrativas
* qualquer operação futura de appointment

Nunca gravar:

* password
* password_hash
* SESSION_SECRET
* tokens
* cookies
* outros segredos

Os `old_data` e `new_data` devem excluir campos sensíveis.

## 2. USERS NÃO TERÁ CRUD PÚBLICO

Remover do escopo da Fase 3:

* `users.controller.ts`
* `users.validator.ts`
* `routes/users.ts`

Não criar CRUD REST público para `/api/users`.

O usuário será criado internamente pelos fluxos:

* criação de CLIENT → users + clients na mesma transaction

Pode existir `users.repository.ts`, pois ele é necessário internamente.

## 3. CONCORRÊNCIA — REGRA IMPORTANTE

Não considerar `SELECT FOR UPDATE` como única garantia contra race conditions.

A garantia definitiva contra agendamentos simultâneos continua sendo fornecida pelas EXCLUDE constraints existentes no PostgreSQL:

* `excl_professional_no_overlap`
* `excl_resource_no_overlap`
* `excl_client_no_overlap`

O fluxo transacional pode usar verificações/locks quando apropriado, mas qualquer erro PostgreSQL `23P01` deverá ser tratado explicitamente como conflito e convertido para HTTP 409.

NÃO alterar as EXCLUDE constraints existentes.

## 6. AUTENTICAÇÃO

Implementar:

* `POST /api/auth/login`
* `POST /api/auth/logout`
* `GET /api/auth/me`

Usar:

* express-session
* connect-pg-simple
* SESSION_SECRET existente
* bcrypt salt rounds 12
* express-rate-limit

Login:

1. validar com Zod;
2. procurar usuário por email;
3. verificar ACTIVE;
4. executar bcrypt.compare;
5. resposta indistinguível para email inexistente/senha errada;
6. `req.session.regenerate()`;
7. armazenar somente dados necessários na session;
8. atualizar `last_login_at`;
9. registrar `USER_LOGIN`;
10. nunca retornar `password_hash`.

Cookie:

* httpOnly=true
* secure=true em production
* sameSite=lax
* maxAge=8 horas
* rolling=true

Rate limit:

10 tentativas por IP a cada 15 minutos.
