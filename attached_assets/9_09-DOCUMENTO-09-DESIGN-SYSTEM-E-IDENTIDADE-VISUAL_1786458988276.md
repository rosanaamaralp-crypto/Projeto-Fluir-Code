# FLUIR DA VIDA OFICIAL

## Documento 09 — DESIGN SYSTEM E IDENTIDADE VISUAL

> **Nota de conversão:** este arquivo foi convertido do PDF original para Markdown para uso como documentação de projeto no Replit. O conteúdo funcional foi preservado; a formatação pode ter pequenas diferenças de extração.

FLUIR DA VIDA OFICIAL
DOCUMENTO 09 — DESIGN SYSTEM E IDENTIDADE VISUAL
Versão: 1.0
Status: Documento oficial para desenvolvimento
Prioridade: ALTA

1. OBJETIVO
Definir a linguagem visual do sistema Fluir da Vida Oficial.

O sistema deverá transmitir:

     • acolhimento;
     • confiança;
     • profissionalismo;
     • cuidado;
     • simplicidade;
     • organização;
     • bem-estar.

A interface não deverá parecer um sistema hospitalar excessivamente frio nem um aplicativo genérico
de agendamento.

2. REFERÊNCIA DE IDENTIDADE
A identidade visual deverá partir da comunicação oficial do Espaço Fluir da Vida e manter coerência
entre:

     • site;
     • redes sociais;
     • agendamento;
     • sistema administrativo;
     • comunicação com clientes.

A página oficial de links apresenta o ecossistema digital da marca, incluindo agendamento e seus
principais canais.

3. PRINCÍPIO VISUAL
A interface deverá seguir:

                                                     1

       Humana na aparência, profissional na operação.

O cliente deverá sentir que está utilizando o ambiente digital do próprio Fluir da Vida, e não um
software terceirizado.

4. LOGOTIPO
O logotipo oficial deverá ser utilizado sempre que disponível em arquivo adequado.

Formatos preferenciais:

     • SVG;
     • PNG com transparência.

Não recriar o logotipo artificialmente.

Não alterar:

     • proporção;
     • tipografia;
     • símbolo;
     • cores oficiais.

5. ÁREA DE PROTEÇÃO DO LOGO
O logotipo deverá possuir espaço livre ao redor.

Nenhum:

     • botão;
     • texto;
     • ícone;
     • borda

deverá encostar no logotipo.

6. VARIAÇÕES
Preparar suporte para:

     • logo principal;
     • logo para fundo claro;
     • logo para fundo escuro;
     • versão reduzida, quando existir.

                                                    2

7. PALETA DE CORES
A paleta definitiva deverá ser extraída/confirmada a partir dos materiais oficiais da marca antes da
implementação final.

Estrutura prevista:

Cor Primária

Usada em:

     • botões principais;
     • links;
     • elementos ativos;
     • destaques.

Cor Secundária

Usada em:

     • elementos complementares;
     • cards;
     • destaques secundários.

Cor de Fundo

Usada em:

     • páginas;
     • áreas de conteúdo;
     • dashboards.

Cor de Superfície

Usada em:

     • cards;
     • modais;
     • menus;
     • formulários.

Cor de Texto Principal

Para títulos e informações importantes.

Cor de Texto Secundário

Para informações auxiliares.

                                                    3

8. CORES SEMÂNTICAS
Independentemente da paleta da marca, o sistema deverá possuir cores semânticas.

Sucesso

Para:

        • confirmado;
        • concluído;
        • disponível.

Atenção

Para:

        • pendente;
        • aviso;
        • atenção.

Erro

Para:

        • erro;
        • conflito;
        • cancelamento.

Informação

Para:

        • informações;
        • orientações;
        • mensagens auxiliares.

Essas cores devem permanecer visualmente distinguíveis da paleta institucional.

9. STATUS DOS AGENDAMENTOS
Padrão visual:

  CONFIRMADO
  CONCLUÍDO
  PENDENTE
  CANCELADO

                                                  4

  EM ATENDIMENTO
  AUSENTE

Cada status deverá possuir:

     • texto;
     • indicador visual;
     • eventualmente ícone.

Nunca utilizar somente cor para comunicar o status.

10. MODALIDADES
PRESENCIAL

Utilizar um indicador visual relacionado ao espaço físico.

HOME CARE

Utilizar indicador visual relacionado a atendimento externo/casa.

Exemplo conceitual:

  📍 Presencial
  🏠 Home Care

Os ícones finais deverão ser definidos pelo Design System.

11. MACAS
A visualização administrativa deverá possuir estados claros:

  Disponível
  Ocupada
  Bloqueada

Exemplo:

  Maca 01      Disponível
  Maca 02      Ocupada
  Maca 03      Ocupada

                                                    5

  Maca 04      Disponível
  Maca 05      Bloqueada

12. TIPOGRAFIA
O sistema deverá utilizar uma família tipográfica moderna, altamente legível e com excelente suporte
para português.

Deverá possuir pelo menos:

     • regular;
     • medium;
     • semibold;
     • bold.

Evitar excesso de pesos.

13. HIERARQUIA TIPOGRÁFICA
Estrutura:

  H1
  Página

  H2
  Seção

  H3
  Subseção

  Body
  Texto principal

  Small
  Informações auxiliares

  Caption
  Informações secundárias

14. BOTÕES
Os botões deverão possuir hierarquia.

                                                  6

Primário

Ação principal:

       Confirmar agendamento

Secundário

Ação alternativa:

       Voltar

Terciário

Ação discreta:

       Ver detalhes

Destrutivo

Ações como:

       Cancelar agendamento

15. BOTÃO PRINCIPAL
O botão principal deverá ser facilmente identificado.

Exemplos:

     • Agendar;
     • Confirmar;
     • Salvar;
     • Continuar.

Não utilizar múltiplos botões primários competindo visualmente na mesma tela.

16. FORMULÁRIOS
Campos deverão possuir:

     • label;
     • campo;
     • estado normal;
     • foco;
     • erro;

                                                    7

      • preenchido;
      • desabilitado.

Nunca depender somente do placeholder para identificar o campo.

17. MENSAGENS DE ERRO
As mensagens deverão ser humanas.

Evitar:

          Invalid field.

Preferir:

          Informe um telefone válido.

18. CONFIRMAÇÕES
Ações importantes deverão apresentar confirmação.

Exemplo:

          Deseja cancelar este agendamento?

Botões:

Voltar

Cancelar agendamento

19. CARDS
Cards serão utilizados principalmente para:

      • próximo atendimento;
      • indicadores;
      • macas;
      • profissionais;
      • serviços.

Não utilizar cards para absolutamente tudo.

                                                8

20. DASHBOARD
O dashboard deverá priorizar:

    1. informação mais importante;
    2. próxima ação;
    3. resumo operacional.

Evitar excesso de gráficos no MVP.

21. AGENDA
A agenda é uma das principais interfaces do sistema.

Deverá possuir:

     • boa leitura temporal;
     • horários claramente separados;
     • identificação do atendimento;
     • profissional;
     • cliente;
     • modalidade;
     • maca quando aplicável.

22. AGENDA — ADMINISTRADOR
Prioridade:

densidade de informação + controle.

Deverá permitir:

     • filtros;
     • mudança de período;
     • visualização de recursos;
     • ações rápidas.

23. AGENDA — PROFISSIONAL
Prioridade:

clareza + rapidez.

                                                  9

Mostrar principalmente:

     • horário;
     • cliente;
     • serviço;
     • modalidade;
     • local;
     • maca quando presencial.

24. AGENDA — CLIENTE
Prioridade:

simplicidade.

O cliente não deverá visualizar informações operacionais desnecessárias.

Exemplo:

  15/08
  14:00

  Drenagem
  Ana

  Presencial

25. MACAS — VISUAL
A área administrativa poderá apresentar as cinco macas como recursos independentes.

  ┌──────────┐
  │ MACA 01     │
  │ Livre       │
  └──────────┘

  ┌──────────┐
  │ MACA 02     │
  │ Ocupada     │
  └──────────┘

                                                  10

26. HOME CARE — VISUAL
Home Care deverá ser reconhecido rapidamente na agenda.

Exemplo:

  14:00
  Maria Silva
  Drenagem
  🏠 Home Care

27. PRESENCIAL — VISUAL
Exemplo:

  15:00
  João Silva
  Atendimento
  📍 Fluir da Vida
  Maca 03

28. ÍCONES
Utilizar uma única biblioteca de ícones no sistema.

Não misturar estilos diferentes.

Os ícones deverão ser:

      • simples;
      • consistentes;
      • facilmente reconhecíveis.

29. ESPAÇAMENTO
Utilizar escala consistente.

Exemplo:

                                                      11

  4
  8
  12
  16
  24
  32
  48
  64

Os valores poderão ser adaptados durante a implementação.

30. BORDAS
Evitar excesso de bordas.

Cards e áreas deverão utilizar principalmente:

       • espaçamento;
       • contraste;
       • superfície;
       • sombra discreta.

31. CANTOS
O sistema deverá possuir padrão consistente de border-radius.

Evitar:

       • alguns elementos muito arredondados;
       • outros quadrados;
       • outros com formatos diferentes.

32. SOMBRAS
Utilizar sombras discretas.

A interface não deverá parecer excessivamente "3D".

33. TABELAS
Tabelas deverão ser utilizadas principalmente no ambiente administrativo.

                                                 12

Exemplo:

  Cliente | Serviço | Profissional | Data | Status

No celular, deverão ser adaptadas ou transformadas em cards/listas.

34. FILTROS
Filtros deverão ser simples e organizados.

Não apresentar dez filtros abertos simultaneamente em telas pequenas.

35. NAVEGAÇÃO
Desktop:

menu lateral

Mobile:

menu inferior ou menu compacto, conforme contexto.

36. DASHBOARD MOBILE
No celular:

     • prioridade para próximo atendimento;
     • ações principais;
     • agenda do dia.

Informações secundárias deverão ficar abaixo.

37. RESPONSIVIDADE
Breakpoints deverão ser definidos de forma consistente.

A interface não deverá simplesmente "encolher".

Elementos deverão reorganizar-se.

                                                  13

38. ACESSIBILIDADE
O sistema deverá considerar:

     • contraste;
     • tamanho mínimo de texto;
     • áreas de toque adequadas;
     • foco de teclado;
     • labels;
     • mensagens de erro;
     • navegação sem depender exclusivamente de cor.

39. ESTADOS DE CARREGAMENTO
Toda operação que depender do backend deverá possuir estado de carregamento.

Exemplo:

  Confirmando agendamento...

Não deixar o usuário sem resposta.

40. ESTADO VAZIO
Quando não houver dados:

Não mostrar apenas uma tela vazia.

Exemplo:

       Você ainda não possui agendamentos.

E, quando aplicável:

Agendar atendimento

41. ESTADO DE ERRO
Exemplo:

       Não conseguimos carregar sua agenda.

                                               14

Ações:

Tentar novamente

42. ESTADO OFFLINE / CONEXÃO
O sistema deverá estar preparado para falhas de conexão.

Não confirmar uma operação localmente como se tivesse sido salva quando o backend não confirmou.

43. IDENTIDADE ENTRE SITE E SISTEMA
O sistema deverá manter coerência com a presença digital do Fluir da Vida.

A página oficial de links funciona como ponto de entrada para os canais digitais da marca, portanto o
sistema de agendamento deverá parecer parte do mesmo ecossistema.

44. TOM VISUAL
O sistema deverá evitar aparência:

     • excessivamente corporativa;
     • hospitalar;
     • agressiva;
     • tecnológica demais;
     • infantil.

Buscar:

acolhedor + profissional + limpo + moderno.

45. FOTOGRAFIA E IMAGENS
Quando forem utilizadas imagens:

     • priorizar materiais oficiais;
     • evitar imagens genéricas incompatíveis com a marca;
     • manter consistência visual;
     • não sobrecarregar telas operacionais.

                                                  15

46. ILUSTRAÇÕES
Ilustrações poderão ser utilizadas em:

     • estados vazios;
     • onboarding;
     • páginas institucionais.

Não são necessárias em todas as telas.

47. MICROINTERAÇÕES
Podem existir animações discretas para:

     • confirmação;
     • abertura de modal;
     • mudança de estado;
     • carregamento.

Evitar animações que atrasem tarefas.

48. EXPERIÊNCIA DE AGENDAMENTO
O agendamento deverá ser a experiência mais importante do sistema.

Objetivo:

       Poucos passos, pouca dúvida e confirmação clara.

49. REGRA DE OURO DA INTERFACE
O usuário deverá saber sempre:

Onde estou?

O que estou fazendo?

O que preciso fazer agora?

O que acontecerá depois?

                                               16

50. DESIGN SYSTEM COMO CÓDIGO
No Replit, o Design System deverá ser centralizado.

Não criar estilos diferentes tela por tela.

Deverão existir componentes reutilizáveis para:

      • Button;
      • Input;
      • Select;
      • Modal;
      • Card;
      • Badge;
      • Calendar;
      • Appointment;
      • EmptyState;
      • Loading;
      • Alert;
      • Navigation.

51. TOKENS
As propriedades visuais deverão ser centralizadas em tokens.

Exemplo conceitual:

  colors.primary
  colors.secondary
  colors.background
  colors.surface
  colors.text
  colors.success
  colors.warning
  colors.error

  spacing.xs
  spacing.sm
  spacing.md
  spacing.lg

  radius.sm
  radius.md
  radius.lg

Os valores definitivos deverão ser configurados conforme a identidade visual oficial.

                                                   17

52. NÃO DUPLICAR ESTILOS
O Agent não deverá criar:

  ButtonGreen
  GreenButton
  PrimaryGreenButton
  ConfirmButton

quando todos representam o mesmo componente.

Deverá existir:

  Button variant="primary"

53. DESIGN SYSTEM E BACKLOG
Novos componentes visuais deverão ser adicionados ao Design System quando forem reutilizáveis.

Não transformar cada nova tela em uma coleção de estilos isolados.

54. REGRA PARA PROTÓTIPOS
Todo protótipo futuro deverá indicar:

  TELA:
  PERFIL:
  OBJETIVO:
  ORIGEM:
  AÇÕES:

Exemplo:

  TELA: Novo Agendamento
  PERFIL: Cliente
  OBJETIVO: Criar atendimento
  ORIGEM: Dashboard
  AÇÕES: Selecionar serviço, modalidade, profissional,
  data e horário

                                                 18

55. REGRA PARA IMAGENS FUTURAS
Qualquer imagem/protótipo produzido para validação deverá conter identificação clara do perfil.

Exemplo:

CLIENTE — NOVO AGENDAMENTO

ou

PROFISSIONAL — NOVO AGENDAMENTO

ou

ADMINISTRADOR — NOVO AGENDAMENTO

Nunca deixar essa informação implícita.

56. REGRA PARA O REPLIT AGENT
Antes de criar qualquer componente:

     1. consultar este Design System;
     2. verificar se o componente já existe;
     3. reutilizar o componente existente;
     4. utilizar tokens;
     5. manter responsividade;
     6. manter acessibilidade;
     7. não inventar nova identidade visual.

57. IDENTIDADE VISUAL — REGRA FINAL
A identidade visual deverá ser:

       reconhecível como Fluir da Vida mesmo sem o usuário visualizar o endereço do site.

58. PRINCÍPIO FINAL
O sistema deverá parecer:

Fluir da Vida primeiro.

                                                 19

E:

software de gestão depois.

A tecnologia deve desaparecer atrás de uma experiência simples, acolhedora e profissional.
