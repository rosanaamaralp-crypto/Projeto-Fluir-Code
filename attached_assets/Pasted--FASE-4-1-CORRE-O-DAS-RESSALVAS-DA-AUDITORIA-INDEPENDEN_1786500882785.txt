# OBS-A — AUDIT LOG DO CANCELAMENTO DURANTE REAGENDAMENTO

Auditoria identificou:

Durante `reschedule()`, o appointment original é alterado para `CANCELLED`, mas é criado somente um audit log:

`APPOINTMENT_RESCHEDULED`

O cancelamento do appointment original não possui seu próprio:

`APPOINTMENT_CANCELLED`

### Correção desejada

Dentro da mesma `db.transaction()` usada pelo reagendamento:

1. Atualizar o appointment original para `CANCELLED`.
2. Registrar o respectivo `appointment_status_history`.
3. Criar um audit log:

`action = "APPOINTMENT_CANCELLED"`

com:

`entityId = appointmentId` do appointment ORIGINAL.

4. Criar o novo appointment.
5. Criar o histórico do novo appointment.
6. Criar o audit log:

`action = "APPOINTMENT_RESCHEDULED"`

conforme o comportamento atual.

### Requisitos

* Tudo deve permanecer na mesma transaction.
* Se qualquer operação falhar, tudo deve sofrer rollback.
* O comportamento atual do reagendamento deve ser preservado.
* Não remover o `APPOINTMENT_RESCHEDULED`.
* Não duplicar audit logs.
* Verificar o formato utilizado atualmente pelos demais audit logs antes de implementar.

Adicionar teste de integração verificando que um reagendamento bem-sucedido produz:

1. `APPOINTMENT_CANCELLED` para o appointment original.
2. `APPOINTMENT_RESCHEDULED` para o reagendamento.
3. histórico de status do appointment original.
4. histórico de status do novo appointment.

# OBS-D — GET /api/slots PARA CLIENT

Auditoria identificou uma inconsistência de UX:

Quando um usuário com role `CLIENT` consulta:

`GET /api/slots`

sem fornecer `clientId`, o serviço não considera os appointments já existentes daquele cliente.

Assim, um horário que será recusado posteriormente pelo `POST /api/appointments` pode aparecer como disponível.

### Correção desejada

Para usuários `CLIENT`:

* derivar o `clientId` exclusivamente da sessão autenticada;
* não confiar em `clientId` enviado pelo cliente;
* usar esse `clientId` na consulta de slots mesmo quando o parâmetro não for informado.

Se o CLIENT enviar um `clientId` diferente do seu:

* não utilizar o ID fornecido;
* utilizar o ID derivado da sessão.

Para ADMIN e demais roles, preservar o comportamento atual.

### Requisitos

Não transformar o GET `/slots` em endpoint de criação/reserva.

Não alterar as regras de disponibilidade.

Não alterar as EXCLUDE constraints.

Não introduzir nova regra de negócio além de garantir que o próprio CLIENT seja considerado no cálculo de disponibilidade.

Adicionar testes cobrindo:

1. CLIENT consulta slots sem `clientId` → usa seu próprio clientId.
2. CLIENT possui appointment no horário → slot não aparece como disponível.
3. CLIENT envia `clientId` de outro cliente → o sistema ignora o ID informado e usa o próprio.
4. ADMIN mantém comportamento atual.

# OBS-E — TESTES DE INTEGRAÇÃO DO REAGENDAMENTO

Esta é a observação de maior prioridade.

Adicionar testes de integração end-to-end para:

`PATCH /api/appointments/:id`

com:

```json
{
  "reschedule": {
    "startDatetime": "..."
  }
}
```

Cobrir obrigatoriamente:

### Teste 1 — CLIENT happy path

CLIENT reagenda seu próprio appointment confirmado.

Esperado:

* HTTP 200
* appointment original → `CANCELLED`
* novo appointment criado
* novo appointment → `CONFIRMED`
* histórico correto para ambos
* audit log `APPOINTMENT_CANCELLED`
* audit log `APPOINTMENT_RESCHEDULED`

### Teste 2 — ADMIN happy path

ADMIN reagenda appointment de um cliente.

Esperado:

* HTTP 200
* operação concluída corretamente
* histórico correto
* audit logs corretos

### Teste 3 — PROFESSIONAL

PROFESSIONAL tenta reagendar.

Esperado:

* HTTP 403
* appointment original permanece `CONFIRMED`
* nenhum novo appointment criado
* nenhum histórico indevido
* nenhum audit log indevido

### Teste 4 — Appointment não CONFIRMED

Tentar reagendar appointment que já esteja:

* `IN_PROGRESS`, ou
* `COMPLETED`, ou
* `CANCELLED`, ou
* `NO_SHOW`

Esperado:

* HTTP 400
* nenhum novo appointment
* estado original preservado
* nenhum audit log de reagendamento

### Teste 5 — Conflito no novo horário

Criar um appointment conflitante no novo horário e tentar reagendar o original para esse horário.

Esperado:

* HTTP 409
* appointment original permanece `CONFIRMED`
* novo appointment não existe
* histórico do original não registra cancelamento
* não existe `APPOINTMENT_CANCELLED` do reagendamento
* não existe `APPOINTMENT_RESCHEDULED`

Esse teste é especialmente importante para comprovar o rollback da transaction.

### Teste 6 — Falha de regra de negócio no novo horário

Cobrir pelo menos um caso em que o novo horário seja inválido por uma regra de disponibilidade já existente.

Esperado:

* erro apropriado
* appointment original permanece `CONFIRMED`
* nenhum novo appointment
* nenhum audit de reagendamento
