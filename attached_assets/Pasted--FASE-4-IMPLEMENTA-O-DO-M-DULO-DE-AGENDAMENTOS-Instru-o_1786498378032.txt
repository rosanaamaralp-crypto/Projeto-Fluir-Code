# 1. OBJETIVO DA FASE 4

Implementar o módulo completo de AGENDAMENTOS (`appointments`) utilizando a arquitetura existente:

Request
→ Route
→ Middleware
→ Validator
→ Controller
→ Service
→ Repository
→ PostgreSQL/Drizzle

A regra de negócio deve ficar no service.

# 7. FLUXO TRANSACIONAL OBRIGATÓRIO

Toda criação de appointment deve ocorrer em:

`db.transaction(async (tx) => { ... })`

Fluxo:

1. Validar payload antes da transaction.

2. Identificar CLIENT autenticado.

3. Confirmar:

   * client existe;
   * client está ACTIVE.

4. Buscar professional.

5. Confirmar:

   * professional existe;
   * professional está ACTIVE.

6. Buscar service.

7. Confirmar:

   * service existe;
   * service está ACTIVE.

8. Confirmar que `professional_services.active = true`.

9. Calcular:

`end_datetime = start_datetime + duration_minutes`

10. Validar antecedência mínima.

Utilizar a configuração já adotada na Fase 3.1:

`SLOT_MIN_NOTICE_HOURS`

Não duplicar regra em vários lugares.

11. Validar antecedência máxima:

`SLOT_MAX_ADVANCE_DAYS`

12. Validar disponibilidade semanal do profissional.

13. Validar blocked_periods.

14. Validar conflito do CLIENT.

15. Validar conflito do PROFESSIONAL.

16. Validar conflito do RESOURCE quando aplicável.

17. Validar regras de modality.

18. Capturar:

`price_at_booking = services.price`

O preço deve ser congelado no momento da criação.

19. Inserir appointment com:

`status = CONFIRMED`

e:

`created_by = session.userId`

20. Inserir `appointment_status_history`:

* old_status = NULL
* new_status = CONFIRMED
* changed_by = session.userId

21. Inserir audit log:

`APPOINTMENT_CREATED`

22. COMMIT.

Qualquer falha deve executar ROLLBACK.

# 8. CONCORRÊNCIA — REGRA CRÍTICA

Esta é uma parte obrigatória da Fase 4.

Não confiar apenas em SELECT prévio.

O PostgreSQL possui EXCLUDE constraints já existentes:

* `excl_professional_no_overlap`
* `excl_resource_no_overlap`
* `excl_client_no_overlap`

Essas constraints são a garantia definitiva contra double-booking.

O código deve tratar:

`23P01`

como:

HTTP `409 Conflict`.

Implementar também proteção transacional adequada contra concorrência.

Não assumir que:

`SELECT ... FOR UPDATE`

em linhas inexistentes é suficiente para impedir duas inserções concorrentes.

A solução deve respeitar as EXCLUDE constraints existentes e permitir que o banco seja a última linha de defesa.

---

# 9. REGRA DE OVERLAP

Usar exatamente:

`slot.start < occupied.end AND slot.end > occupied.start`

Não usar comparação baseada somente em igualdade de horários.

---

# 10. RESOURCE / IN_PERSON

Regra:

Se:

`modality = IN_PERSON`

deve existir um resource compatível e disponível.

O appointment deve possuir `resource_id` quando o schema/regra existente exigir.

Nunca permitir que dois appointments utilizem o mesmo resource simultaneamente.

A EXCLUDE constraint existente deve permanecer como garantia definitiva.

Se o client não fornecer resourceId, o service deve selecionar automaticamente um resource disponível compatível, caso essa seja a regra definida pelo schema/arquitetura.

Não escolher resource aleatoriamente sem verificar disponibilidade dentro da transaction.

Se não houver resource disponível:

`409 Conflict`

---

# 11. REMOTE

Para:

`modality = REMOTE`

não consumir resource físico.

Respeitar exatamente os valores permitidos pelo schema existente.

Não inventar nova modalidade.

# 13. AUTORIZAÇÃO

Implementar RBAC utilizando os middlewares existentes.

CLIENT:

* pode criar appointment para si;
* pode visualizar seus appointments;
* pode cancelar/remarcar seus appointments conforme regras;
* nunca pode acessar appointments de outro client.

PROFESSIONAL:

* pode visualizar seus próprios appointments;
* pode alterar status dos seus appointments quando permitido;
* nunca pode acessar appointments de outro professional.

ADMIN:

* acesso administrativo conforme arquitetura existente.

Não duplicar autenticação dentro dos controllers quando middleware já resolver.

Ownership deve ser verificado no service/repository quando necessário para garantir isolamento.

# 15. CANCELAMENTO

Implementar:

PATCH `/api/appointments/:id`

com:

```json
{
  "status": "CANCELLED",
  "reason": "..."
}
```

A operação deve ser transacional.

Dentro da transaction:

1. buscar appointment;
2. verificar ownership/RBAC;
3. validar que o status atual permite cancelamento;
4. alterar status;
5. inserir appointment_status_history;
6. inserir audit_logs;
7. commit.

Não permitir cancelar appointment já:

* CANCELLED
* COMPLETED
* NO_SHOW

sem uma regra explícita.

# 17. REMARCAÇÃO

Não criar status RESCHEDULED.

Implementar remarcação como operação transacional:

BEGIN

1. validar appointment original;
2. verificar autorização;
3. validar novo horário;
4. cancelar appointment original;
5. inserir history do cancelamento;
6. criar novo appointment;
7. inserir history do novo CONFIRMED;
8. inserir audit logs;
9. COMMIT.

Se qualquer etapa falhar:

ROLLBACK completo.

Os campos existentes em `appointment_status_history`:

* old_start_datetime
* new_start_datetime
* etc.

devem ser utilizados conforme o schema existente.
