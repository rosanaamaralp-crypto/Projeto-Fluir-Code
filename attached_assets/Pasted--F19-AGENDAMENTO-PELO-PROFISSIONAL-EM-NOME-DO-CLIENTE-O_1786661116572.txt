# F19 — AGENDAMENTO PELO PROFISSIONAL EM NOME DO CLIENTE

## OBJETIVO

Implementar exclusivamente a funcionalidade que permite ao usuário PROFESSIONAL criar um agendamento em nome de um CLIENTE.

Este requisito já existe na documentação do projeto e foi confirmado como ausente no código atual.

O sistema deve continuar permitindo que:

- CLIENT crie seu próprio agendamento;
- ADMIN crie agendamentos conforme as permissões existentes;
- PROFESSIONAL crie agendamentos para seus próprios clientes.

## ESCOPO AUTORIZADO

### 1. BACKEND

Alterar o POST /api/appointments para permitir também o perfil PROFESSIONAL.

Regra de segurança obrigatória:

Quando o usuário autenticado for PROFESSIONAL:

- `professionalId` NÃO deve ser livremente escolhido pelo cliente da API;
- o backend deve determinar o profissional a partir da sessão/autenticação;
- o profissional só pode criar agendamento para SI MESMO;
- `clientId` será informado para identificar o cliente atendido.

Não confiar no `professionalId` enviado pelo frontend.

Se o contrato atual exigir `professionalId`, adaptar da forma mínima e segura possível, preferencialmente ignorando/substituindo esse valor para PROFESSIONAL pelo ID do profissional autenticado.

### 2. CLIENTE

O PROFESSIONAL poderá selecionar um cliente existente.

NÃO implementar cadastro de novo cliente durante o agendamento nesta fase.

O cadastro de novos clientes continua sendo responsabilidade do ADMIN.

Se não houver clientes cadastrados, a interface deve informar claramente que é necessário cadastrar o cliente antes de realizar o agendamento.

### 3. SERVIÇOS

O PROFESSIONAL deve visualizar somente serviços que estejam vinculados a ele.

Reutilizar a vinculação de serviços já existente.

Não permitir que o profissional agende um serviço que não esteja vinculado a ele.

Essa validação deve existir no backend, não somente no frontend.

### 4. MODALIDADE

Preservar integralmente as regras existentes:

- IN_PERSON;
- HOME_CARE.

Para IN_PERSON:

- utilizar o mecanismo existente de seleção de maca;
- preservar EXCLUDE constraint;
- não permitir double-booking.

Para HOME_CARE:

- selecionar/utilizar endereço pertencente ao CLIENTE;
- preservar todas as validações existentes.

Não alterar as regras atuais de agendamento.

### 5. DISPONIBILIDADE

O agendamento criado pelo PROFESSIONAL deve respeitar:

- disponibilidade do próprio profissional;
- bloqueios;
- conflitos de cliente;
- conflitos de profissional;
- conflitos de maca;
- duração do serviço;
- demais regras existentes.

Não duplicar regras já existentes.

Reutilizar o service/repository existente.

### 6. FRONTEND PROFESSIONAL

Adicionar uma ação claramente identificada:

**Novo agendamento**

Preferencialmente na área de:

- Minha Agenda;
- ou Dashboard;
- ou menu do PROFESSIONAL,

seguindo o padrão visual já existente.

Criar o fluxo utilizando o máximo possível do wizard existente do CLIENT.

Fluxo desejado:

1. Selecionar CLIENTE;
2. Selecionar SERVIÇO;
3. Selecionar MODALIDADE;
4. Selecionar DATA;
5. Selecionar HORÁRIO disponível;
6. Se presencial, selecionar/reservar MACA conforme mecanismo existente;
7. Se home care, selecionar ENDEREÇO do cliente;
8. Exibir resumo;
9. Confirmar;
10. Exibir sucesso.

O profissional NÃO precisa selecionar outro profissional.

O profissional autenticado será automaticamente o profissional do atendimento.

### 7. REUTILIZAÇÃO

Evitar duplicação de código.

### 8. OPENAPI / CODEGEN

Se for necessário:

3. não alterar endpoints não relacionados;
4. não fazer limpeza geral da OpenAPI.

Se o contrato atual já suportar os campos necessários, não modificar OpenAPI apenas por documentação.

### 10. SEGURANÇA

- CLIENT continua podendo criar apenas para si;
- ADMIN mantém comportamento atual;
- PROFESSIONAL só consegue criar para si próprio;
- PROFESSIONAL não consegue criar appointment usando outro `professionalId`;
- PROFESSIONAL não consegue agendar cliente inexistente;
- PROFESSIONAL não consegue usar serviço não vinculado a ele;

- regras de conflito continuam funcionando.

Não enfraquecer nenhuma regra de RBAC/ownership existente.
