- disponibilidade do profissional
- disponibilidade do serviço, se aplicável
- blocked periods
- conflitos de agenda
- resource/maca
- endereço
- modalidade
- demais validações já existentes

NÃO criar uma segunda implementação paralela dessas regras se já existir função reutilizável.

4. PROFISSIONAL

Quando professionalId mudar:

- usar a mesma lógica de disponibilidade já utilizada no create/reschedule;
- confirmar que o novo profissional atende ao serviço;
- confirmar conflitos;
- confirmar tenant/ownership;
- confirmar se o profissional pode executar aquele appointment.

Não assumir que apenas trocar professionalId no banco é suficiente.

5. IN_PERSON → HOME_CARE

Confirmar a sequência correta:

- liberar resource/maca atual;
- resourceId deve ficar NULL;
- addressId deve ser obrigatório;
- validar endereço;
- validar disponibilidade;
- manter integridade da EXCLUDE constraint;
- realizar tudo atomicamente.

6. HOME_CARE → IN_PERSON

Confirmar:

- addressId deve deixar de ser utilizado;
- encontrar/reservar resource/maca válido;
- validar disponibilidade;
- resourceId deve ser preenchido;
- addressId deve ficar NULL;
- respeitar EXCLUDE constraint.

7. IN_PERSON → IN_PERSON

Se apenas profissional/data/endereço mudar:

- manter/resolver resource conforme as regras existentes;
- não liberar indevidamente a maca atual antes da nova disponibilidade ser validada.

8. HOME_CARE → HOME_CARE

Se mudar profissional/data/endereço:

- revalidar disponibilidade;
- manter resourceId NULL;
- manter addressId válido.

9. HORÁRIO

Se startDatetime mudar:

- descobrir durationMinutes do appointment;
- calcular endDatetime;
- NÃO permitir que o caller controle livremente endDatetime;
- enviar startDatetime + endDatetime ao repository.

10. TRANSAÇÃO

Mapear exatamente onde deve começar a transação.

A operação precisa ser atomicamente:

validar estado atual
→ validar permissões
→ carregar dados necessários
→ validar nova configuração
→ validar disponibilidade
→ determinar/liberar/reservar recurso
→ atualizar appointment
→ registrar histórico
→ registrar audit log
→ commit

Em caso de qualquer erro:

→ rollback completo

IMPORTANTE:
Não aceitar uma arquitetura em que a maca antiga seja liberada definitivamente antes da nova configuração estar validada.
